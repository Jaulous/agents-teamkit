# Team Review Rubric

用本 rubric 审查已有 TeamKit 团队定义。先记录文件中的证据，再写结论；机械维度可以确定断言，涉及业务依赖的维度必须降格为 `[推断]` 或 `[提问]`。每一节末尾的“建议收益”可直接复用到面向用户的报告中。

## A 桶 · 结构正确性（防假并行）

### A1 · 混边死区

- 判定：机械。
- 怎么判：按每个源节点统计 `relation: parallel` 出度 P 和未标记/choice 出度 C。若 P≥1 且 C≥1，记录源节点、各目标和边定义。
- Good：一个源节点要么全是并行边（真正同时启动），要么是互斥选择边；若业务上既要条件又要并行，把条件放入分支内部或拆成明确的前置步骤。
- Weak：同一源节点混有 parallel 和 choice。Core 不提供隐式 fork 命令，parallel 支路没有可激活的路径。
- 严重度：`blocker`。
- 建议收益：消除二义性，让每条业务路径都有明确的启动方式。

### A2 · join 一致性

- 判定：机械。
- 怎么判：统计每个目标节点的 parallel 入边数，并与节点上的 `join` 属性对照。`join: all` 但入边少于 2 是死声明；入边多于 1 但没有 `join: all` 只是文档标注缺失。
- Good：真正收束多个 parallel 前置时使用 `join: all` 作为可读标注；不把缺少标注当成运行缺陷。
- Weak：写了没有意义的 `join: all`，或报告“缺 join 就无法运行”。引擎只按 parallel 入边数判定 join。
- 严重度：`info`（两种情况均为可读性问题，不得报 warning）。
- 建议收益：让维护者一眼看懂哪里是汇总点，同时避免把合法图误报成故障。

### A3 · join 前置可满足性

- 判定：机械。
- 怎么判：从 `process.graph.entry` 做可达性和同轮激活分析；对每个 join 目标列出全部 parallel 前置，检查是否存在从 entry 不可达、被混边阻断或不可能在同一轮完成的前置。
- Good：每个 join 前置都有一条能从入口启动并最终完成的 parallel 路径。
- Weak：join 等待一个永远不会完成的前置，Topic 会保持 waiting；这是由定义可证明的永久等待，不需要运行数据才能指出。
- 严重度：`warning`。
- 建议收益：在设计期发现无法收束的步骤，避免流程留下无人处理的等待项。

### A4 · 单条 parallel 边

- 判定：机械。
- 怎么判：找出 source 的 parallel 出度恰好为 1，且没有第二条 parallel 边参与同一 fork。
- Good：只有需要同时激活至少两个分支时才使用 parallel；单一路径使用普通边表达。
- Weak：单条 `relation: parallel` 边。它是恒等变换，不产生 fork，也不会触发警告。
- 严重度：`info`。
- 建议收益：减少误导性标记，让团队定义更简洁、更容易理解。

### A5 · 节点级 `max_visits`

- 判定：机械。
- 怎么判：复用 `teamkit team validate` warning，并扫描所有 graph node 是否出现 `max_visits`。Core 只消费边级 `max_visits`，节点级字段会被忽略。
- Good：把循环上限写在会回到节点的具体 edge 上，并说明允许回访的业务条件。
- Weak：在 node 上写 `max_visits`，以为它能限制节点被访问次数。
- 严重度：`warning`。
- 建议收益：让回环真正受到约束，避免定义者以为已有保护而实际没有。

### A6 · 图可达性

- 判定：机械。
- 怎么判：从 entry 做 BFS/DFS，列出未被访问的 node ID，并检查是否只有孤立入边、拼错 source 或永远被 choice 条件绕过。
- Good：每个业务节点都有从 entry 出发的明确路径；有意保留的模板节点应在定义外说明，而不是放进可执行图。
- Weak：节点存在于 YAML，却没有任何从入口可达的路径。
- 严重度：`warning`。
- 建议收益：避免维护一段实际上不会执行、却会误导协作者的流程定义。

### A7 · 无界回环

- 判定：机械为候选，严重度按证据保持 `info`。
- 怎么判：在图上找回到已发生节点的环；检查环上是否至少有一条边带 `max_visits`。记录环的 node/edge ID，不预测运行次数或性能。
- Good：允许的回环在返回边上设置清晰的 `max_visits`，并用 `when` 说明何时返工。
- Weak：存在回路但没有任何边级上限，或只把上限写在节点级。
- 严重度：`info`（此 rubric 不把未设上限直接描述成运行期故障）。
- 建议收益：让返工边界可见，便于后续运行复盘和成本估算。

## B 桶 · 并行能力

### B1 · 可并行化链识别

- 判定：机械列候选 + LLM 收窄。
- 怎么判：从串行链中找相邻步骤，读取对应 profile 的 Inputs/Outputs/Responsible For；若后一步没有声明读取前一步产物，列为候选并行对，并指出证据文件与字段。
- Good：只有互不读取对方中间产物、且可独立完成的步骤才进入 parallel 候选；汇总节点明确消费两边结果。
- Weak：仅凭“看起来是两个专家”就改成并行，未核对画像中的输入、输出或共享上下文。
- 严重度：`[推断]` / `[提问]`，不单独定为 blocker。
- 建议收益：把可能同时推进的工作找出来，同时避免把有依赖的步骤错误拆开。

### B2 · 隐含依赖 vs parallel 声明冲突

- 判定：LLM 主导。
- 怎么判：先机械列出所有 parallel 相邻节点，再对照后节点 profile 是否明确写“读取/等待/使用前节点产物”。若有冲突，只提出用户确认，不断言引擎一定产生错误结果。
- Good：parallel 只用于业务上独立的输入；存在依赖时改为顺序边，或增加真正的中间产物/汇总步骤。
- Weak：YAML 声明同时做，但画像却要求后节点先拿到前节点结论。
- 严重度：`[提问]`；若用户确认存在依赖，再给最小改动方案。
- 建议收益：先确认业务依赖再动图，避免为了“并行”牺牲结论正确性。

### B3 · 聚合节点提示

- 判定：机械信号 + LLM。
- 怎么判：找出 fork 目标 expert 与 coordinator 相同的节点；再读取该节点 task 是否只是“收集多个子任务/汇总各方意见”。这是候选信号，不自动要求拆分。
- Good：协调者负责启动与汇总，成员节点分别承载可独立的工作，最终由明确的 join/汇总节点收束。
- Weak：一个 coordinator-owned 节点包揽多个本可独立的子任务，或 fork 目标仍全部回到同一聚合节点而没有成员工作节点。
- 严重度：`[推断]` / `[提问]`，通常 `info`。
- 建议收益：把可独立的工作交给真正的成员节点，减少协调者成为单点瓶颈的可能。

## C 桶 · 通信定义

### C1 · required 扇出普查

- 判定：机械计数 + LLM 分级。
- 怎么判：读取 `process.communication.default_response`，逐条列出 `rules` 中 `response: required`，并制作每个 expert 的出度/入度表。然后请用户判断每条是“继续前必须拿到的门节点回复”，还是“派发通知/可稍后到达的协作消息”。
- Good：缺省为 `optional`；只有交接、汇总、报告、裁决等真正阻塞业务的门节点显式 `required`。
- Weak：default 和大量派发规则都设成 required，却没有说明为什么每条回复都必须阻塞推进。
- 严重度：`warning`。
- 建议收益：把强制等待留给真正的门节点，减少不必要的往返与协调负担。

### C2 · 图边 vs rules 重复

- 判定：机械。
- 怎么判：规范化比较每条 rule 的 `from → to` 与 graph edge 两端专家；若两者重合且 rule 没有额外 `when` 或特殊 `response`，记录重复授权。
- Good：图边负责默认的步骤间许可，communication rule 只补充额外条件、例外或不同回复要求。
- Weak：把每一条图边原样复制到 rules，造成两个地方都像是权限来源。
- 严重度：`info`。
- 建议收益：减少重复配置，降低修改一处却漏改另一处的维护风险。

### C3 · 回传通道缺失

- 判定：机械算许可 + LLM 判必要。
- 怎么判：对每个 fork 支路到汇总/合成 expert，检查 graph edge、communication rule 和 `allow_expert_requests` 是否至少提供一条许可路径；再由用户确认该回传是否是业务必需。
- Good：每个并行成员都能把结果交给汇总者，通道的必要条件和响应要求可追溯。
- Weak：分支能启动，却没有 edge、rule 或允许请求的通道把结果送回汇总者。
- 严重度：`warning`。
- 建议收益：确保并行工作不会“做完却没人收到”，让汇总步骤有完整输入。

### C4 · 门节点缺 required

- 判定：机械列候选 + LLM 判定。
- 怎么判：列出 join 前置边和最终合成边对应的专家对；若该路径没有显式 `response: required` 且 default 为 optional，标为“候选门节点”，再让用户确认是否必须等回复。
- Good：真正决定能否汇总、发布或裁决的回复显式 required；普通通知保持 optional。
- Weak：最终报告或 join 所需的关键结果依赖缺省 optional，定义却没有说明如何等待。
- 严重度：`warning`（业务确认后成立）。
- 建议收益：让汇总/发布不会在关键输入尚未到达时被误推进。

## D 桶 · 团队一致性

### D1 · 专家参与度

- 判定：机械。
- 怎么判：统计 expert 在 graph nodes 中出现次数、入度、出度；标记零节点 expert，以及同一 expert 被多个 parallel 节点同时指向的静态单实例信号。
- Good：每个声明参与的 expert 至少拥有清晰节点或明确通信职责；并行分支使用能独立承载工作的成员角色。
- Weak：画像存在但从未被图或规则引用，或多个并行节点都指向同一 expert，职责与单实例适配器能力不清。
- 严重度：`info`。
- 建议收益：清理“名义参与”或确认单实例约束，减少团队结构与实际执行不一致。

### D2 · 输出/人工门匹配

- 判定：LLM。
- 怎么判：读取 `output.sections`、最终合成节点 task、`human_review.required_when`，逐项检查并行分支的异常结果、证据缺口和冲突是否有承接位置。证据指针写明文件、节点和 section。
- Good：最终节点负责产出所有声明 section；高风险、证据不足、规则冲突等条件与人工复核入口对应。
- Weak：输出要求包含某字段却没有任何节点负责，或并行分支异常没有进入最终报告/人工门。
- 严重度：`[推断]` / `[提问]`，通常 `warning`。
- 建议收益：让团队产出的报告和人工决策覆盖定义中承诺的全部结果。
